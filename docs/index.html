In plain terms

The question. A new virus turns up. Which of its proteins should a drug aim at? Picking that target is normally expert judgement — reading the literature, and comparing the new virus to ones that are already understood.

What this does. It takes one accession number — the public database ID for a genome — and nothing else. From that it works out which proteins the virus makes, ranks them by how promising a drug target each one looks, checks whether a drug would have anywhere to grip, and predicts one protein's 3-D shape. Five steps, about a minute and a half, with no person naming the target.

The test below. It was given SARS-CoV-2 — with SARS-CoV-2 itself removed from everything it was allowed to look up, so it could not simply recognise the answer. It still put the real drug targets at the top, including the one an approved antiviral already hits.

Run it on your own pathogen

any NCBI genome

One nucleotide accession is the whole input. No target name, no shortlist, no structure. The same five steps you just read run against the same live databases, and the result becomes a page like this one.

Open the request form

For a genome split across segments, separate the accessions with commas. A genome too large to be viral is refused rather than ranked: this is antiviral work, and the reference it identifies against is reviewed viral proteins.

1 · you This opens a prefilled issue on GitHub. You need an account there; nothing else is asked of you.
2 · the machine A GitHub Action runs the real chain against NCBI, UniProt, PDBe, RCSB and ESMFold. Two to five minutes.
3 · the result A page is written from the record and linked back in a comment on your issue. It also joins the run list.

From a genome to a ranked shortlist

Five steps, run live against public databases. Everything below this line is the path to the deliverable: a list of candidate targets, ranked, with every score decomposed and every surface either measured or refused with a reason.

The toolkit

10 tools · 91 calls

Ten tools in all, each calling live public biology databases. Four of them are called by the five steps above, and section 04 details every call those steps made — the second step's two, intake.decompose and intake.rank_score, are functions in the same module rather than separate registered tools. The rest are reachable from the same four facts step 1 produces, and were exercised separately to record what they cost and how they fail. Deliberately bad inputs are included, so each failure mode is on record rather than assumed.

Evidence on the top targets

15 calls

Five tools the chain itself never calls, run on the highest-ranked targets after the ranking was already final. Nothing refuses them: the cost gate admits all five, because it turns a tool away only when its declared worst case is strictly greater than the budget, and the default budget is 600 seconds — so bioactivity.prior_binders, declaring exactly 600, is admitted. What keeps them off the path is measured cost rather than declared cost: about 210 seconds for one target across the five, against a chain that finishes in 86 seconds. Nothing they return changes a rank. What “AlphaFold DB” served the provenance of the counts above 54 models · 0 from AlphaFold

Every structures.predicted row above is labelled AlphaFold DB · 3D-Beacons and reports a bare predicted_model_count, which reads as though AlphaFold modelled these proteins. It did not. The tool reports the host that served each model separately from the tool that computed it, and for these accessions the two disagree: of 54 predicted models, 35 were served by the AlphaFold host and 0 were computed by AlphaFold — they are ColabFold v1.5.2 models, which run the same weights behind a different alignment pipeline. The chain record cannot carry this, because its summariser reduces the model list to a count on purpose; it is read here from runs/predicted_models.json.
